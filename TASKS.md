## Version 2 Phase 2 — Data reliability and reproducibility (authorized 2026-11-20)
Governance: `DECISIONS.md`, 2026-11-20, "Version 2 Phase 2 (data reliability) scope approved". The charter name for this phase is "Data reliability" (`docs/version_2_charter.md`, section 8). Each item below needs its own scoped branch, validation evidence, and owner review before merging. Phase 2 authorization does not approve every proposed change. Phase 2 changes no Version 1 target, features, model, intervals, final holdout, or recorded results.

Milestone acceptance criteria. Phase 2 is complete only when criteria 1–7 hold:
- [ ] 1. **Provenance and lineage manifest.** A committed manifest records, for every raw source file the app and tests use: filename, source URL, publisher, retrieval timestamp (UTC, recorded at download time, never inferred), publication or release date when verifiable plus the evidence for that date (otherwise "unverified"), SHA-256, size, and a licensing/redistribution note. For every derived artifact that feeds a displayed or forecast number, it records the producing script and git commit, its input fingerprints, and its output fingerprint. A test verifies local files against the manifest when they are present. This clears the groundwork for TD-03 and TD-25.
- [ ] 2. **PJM portability (TD-03).** Screening takes `retrieved_at` from the manifest, not `st_birthtime`. With the workbooks present, the PJM view returns values on Linux, proven by a CI test. A missing manifest entry still yields `RETRIEVAL_UNAVAILABLE`, and no time is invented. Needs its own dated `DECISIONS.md` entry (the provenance semantics change). `RISK_REGISTER.md` R9 is updated.
- [ ] 3. **Reproducibly locked environment (TD-02).** Every dependency of the Python (`dev`, `demo`, `api`) and Node parts is pinned through the repository's authoritative lockfile or lockfiles. CI and `README.md` install from those locks, not from unconstrained resolution. The tool choice is recorded as a dated decision, and any new tool needs owner approval first.
- [ ] 4. **Machine-enforced data-distribution policy (TD-04).** From EIA's and PJM's published terms, each dataset is classified as committed, reproducibly fetched, local-only (not distributed), or unavailable, recorded in a dated decision with sources. A CI check enforces it (for example, no local-only file is tracked). Report the resulting CI skip count, with a reason for each remaining skip.
- [ ] 5. **EIA vintages and publication timing (TD-25).** A research memo, citing authoritative sources, determines how far historical EIA vintages can be reconstructed. Where reconstruction is impossible or incomplete, the limitation is documented, and no vintage is synthesized or back-filled. A forward archive stores each new release as an immutable, fingerprinted snapshot. Publication timing is measured at the level the source actually varies (release or dataset level unless state-level differences are evidenced), confirming or replacing the assumed m+3 lag. A dated decision sets the vintage policy Phase 3 will use.
- [ ] 6. **Dependency cleanup (TD-01).** DuckDB and Matplotlib are either used with a documented purpose or removed, and the docs match.
- [ ] 7. **Phase 2 validation gate.** CI is green throughout. No test is deleted, weakened, skipped, or xfailed to pass. Version 1 raw files are unchanged. No paid services are used. The frozen final holdout is not rerun, redefined, re-scored, replaced, or used to inform any Phase 2 design decision, and the existing holdout evidence remains immutable.
