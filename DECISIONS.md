## 2026-11-23 - PJM retrieved_at comes from the data manifest, not file-creation time (Phase 2 criterion 2)
**Decision:** The PJM screening view (Streamlit and API) takes each Tables workbook's `retrieved_at` only from `data/manifest.json`, and only when that entry's `retrieved_at.status` is `recorded`. Before the time is used, the local workbook's SHA-256 and size must equal the manifest entry. On a mismatch, screening refuses with `FILE_MISMATCH` and shows neither numbers nor the manifest time. A missing or unreadable manifest, a missing entry, or an entry that is not `recorded` yields `RETRIEVAL_UNAVAILABLE`, and no time is invented. File-system times (`st_birthtime`, modification time) are no longer used as provenance. The parse cache key uses name, size, `st_mtime_ns`, `st_ctime_ns`, and the manifest file's identity only to detect a changed file. Each source row carries its own workbook's recorded time. The retrieval note quotes the manifest evidence and states that it is not a PJM publication date. Vintage availability and as-of selection keep using the PJM release and revision dates in `src/infralens/screening/pjm_sources.py`, unchanged. This replaces the file-creation-time rule described in `TASKS.md` (Phase 1A known limitation) and `RISK_REGISTER.md` R9. It does not edit any earlier entry.
**Evidence:** Pull request #17 (`3867791`) added the manifest. On 2026-11-20 both workbooks were re-downloaded from their PJM URLs and found byte-identical to the stored files (2025: completed 2026-11-20T22:08:52.810329Z; 2026: 2026-11-20T22:08:53.714814Z). The original 2026-10-14 download time was never recorded. TD-03 in `docs/technical_debt_assessment_v2.md`. Before this change the Linux runner could not show PJM numbers (pull request #10, 2026-11-13). A CI test now runs the real parsers and `/api/v1/pjm/screen` on Linux with synthetic workbooks and a test manifest, and fails if creation time is read. A local full-data run with the real workbooks shows the published values with the manifest times.
**Alternatives considered:** Keep `st_birthtime` on macOS and use the manifest only on Linux (rejected: two provenance rules, and creation time is inferred). Use the observed creation time recorded in the manifest (option a, rejected 2026-11-20: inferred). Trust the manifest time without a hash check (rejected: a replaced file would inherit a time it never had). Fall back to a file-system time when the manifest has no recorded entry (rejected: invents provenance).
**Impact:** The displayed PJM `retrieved_at` changes from the local file-creation time (2026-10-14T18:25:52.781338Z) to each workbook's recorded re-download time on 2026-11-20. Any replaced or newly added workbook now needs a recorded manifest entry with a matching SHA-256, or screening refuses. The API response shape is unchanged. Refusals keep 404 `artifact_missing` and 500 `artifact_invalid`, with distinct messages. No change to screening math, zone handling, publication dates, the EIA path, data files, or the frozen holdout. `RISK_REGISTER.md` R9 is updated and TD-03 is resolved.
**Revisit trigger:** A workbook is replaced or a new vintage is added, or the Phase 2 criterion 4 distribution policy changes how the workbooks are stored or fetched.
